# MedClub V0.11 design direction

## Concept: the living clinical canvas

The page builder extends the V0.10 control room without becoming a generic rectangular CMS. Dark instrument controls frame a warm page canvas. Red diagnostic pulses identify active state, while the actual page remains readable and close to its public appearance.

## Signature behavior

- The page library introduces CMS activity through a restrained node signal rather than dashboard decoration.
- Palette icons perform a short instrument check on hover.
- The canvas narrows smoothly between desktop, tablet and phone frames.
- Selected blocks expose a floating instrument strip with drag, move, duplicate and delete controls.
- Audience and schedule rules remain visible as annotations instead of being hidden in settings.
- Autosave behaves like a quiet cloud signal; it never blocks composition.
- Preview uses the exact structured block renderer used inside the canvas.

## UX rules

- The page is data, not hard-coded JSX or arbitrary HTML.
- Drag and drop is never the only reordering mechanism.
- Published edits return to draft until explicitly republished.
- Publishing and scheduling save the latest canvas first.
- Restoration creates a new draft revision and keeps all milestone history.
- Local image uploads are visibly described as preview-only.
- Status, audience and save state always include text, not only color.

## Responsive and accessibility rules

- Desktop uses a three-zone palette, canvas and inspector workbench.
- Medium layouts keep the canvas primary and move the inspector below it.
- Phones present canvas, block library and inspector in task order above the existing admin dock.
- Navigation and editor scrollers hide native bars while retaining touch, wheel and keyboard scrolling.
- Arabic uses logical layout and localized page and block content.
- Reduced motion removes scans, orbiting, pulses and width interpolation.

## Honest boundary

V0.11 is a complete front-end CMS preview backed by device-local structured documents. Its Publish action updates the preview repository; it does not deploy a public website. Production needs a server publishing pipeline, validated rich text, durable media storage, scheduling jobs, cache invalidation, permissions and immutable audit integration.
